# Buffered repair memory measurement — 2026-10-15

The reader helper and string-to-writer API showed similar whole-process peak
RSS on these cases: approximately 49.8 MiB for an 8 MiB ASCII Markdown argument,
and 29.4 MiB for an 8 MiB UTF-8 argument. RSS grows with input size; this is not
constant-memory repair. These measurements alone do not justify an incremental
parser rewrite: there is no production size distribution, concurrency budget,
or requirement for repairing an unfinished stream in this experiment. Keep the
existing byte budget and EOF boundary; measure the consuming application's
payload sizes and memory budget before deciding on a parser redesign.

## Inputs and scope

- `public-heading` is the exact 29-byte **synthetic** reproducer 1 published in
  [OpenBitFun's feedback](https://github.com/GCWing/OpenBitFun/issues/3229#issuecomment-6030422809):
  `{"plan": # Markdown heading"}`. It is not a production payload.
- `markdown-*` repeats the escaped Markdown content shape from
  [`examples/tool_arguments.rs`](../../examples/tool_arguments.rs), with an
  omitted opening value quote and preserved comment markers.
- `unicode-*` repeats the Chinese/emoji content of the truncated query shape in
  [`tests/downstream_contract_tests.rs`](../../tests/downstream_contract_tests.rs),
  omitting the closing quote and brace. The large variants of both shapes are
  explicitly synthetic amplification, not observed downstream request sizes.
- Sizes target 1 KiB, 64 KiB, 1 MiB and 8 MiB of content; full input byte counts
  below include syntax and rounding up to a complete repeated unit.
- Both modes enable comment preservation and unquoted escape decoding, with no
  byte limit. They write to `/dev/null`; neither parses a `serde_json::Value` or
  accumulates a second caller-owned output. `string` reads a file to `String`
  and calls `jsonrepair_to_writer_with_options`; `reader` passes a `BufReader<File>`
  to `jsonrepair_reader_to_writer_with_options`. Generation runs in Python
  before spawning the measured process and is excluded from its RSS.
- An untimed warmup per case/mode parses the output and checks the **entire
  expected content**, including decoded newlines and preserved Unicode. Each
  measured sample is then a fresh process; three samples per case/mode, 54 total.

Every raw numeric sample is committed in
[`memory-20261015.csv`](memory-20261015.csv). MiB means 1,048,576 bytes.
The small public reproduction establishes a process baseline, not a baseline
that can simply be subtracted to recover precise parser allocations. ASCII and
UTF-8 occupy different numbers of `Vec<char>` elements per input byte; allocator
capacity also affects the scaling. This is not a universal six-times memory
multiplier. The writer sink excludes any additional output buffering by callers;
serde values, multiple simultaneous repairs, and application overhead can add
memory. A byte budget bounds admitted input, not total memory or reader time.

## Reproduce

```sh
CARGO_BUILD_JOBS=2 cargo build --locked --release --example memory_probe
python3 scripts/memory_report.py --output target/memory-report
```

The script saves exact input files and hashes, environment/tool versions,
commands, all 54 raw `/usr/bin/time` outputs, numeric JSON results and a Markdown
table in the selected output directory. Results will depend on the machine,
allocator, toolchain and concurrent load. Use Criterion for parser-only timing;
this experiment adds no CI performance threshold or new runtime configuration.
